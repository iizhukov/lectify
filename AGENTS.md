# Lectify

Платформа обработки аудио и видео: файл → workflow → плагины → конспект и другие артефакты.
Переносим возможности `old_monolit` в микросервисы. Приложение ещё не готово к выпуску.
Эти правила действуют для всего репозитория.

## Архитектура

- Сервисы приложения общаются только по gRPC. Клиентский HTTP API и интерфейс будут позже.
- HTTP внешних провайдеров, Vault и S3 не является межсервисным API приложения.
- Каждый плагин запускается в отдельном Docker-контейнере с агентом. Оркестратор управляет запуском и потоками данных.
- Нужна работа нескольких реплик сервисов и нескольких Docker-узлов. Владение исполнением хранится в БД, а не только в памяти процесса.
- Общая инфраструктура генерируется; бизнес-логика и правила доступа принадлежат приложению.

## Структура

- `services/` — сервисы; `service.yaml` описывает настройки, `src/` содержит бизнес-код.
- `proto/` — gRPC-контракты сервисов и плагинов.
- `plugins/` — плагины, их манифесты и обработчики.
- `utils/codegen/` — кодогенератор: модели, генераторы и Jinja2-шаблоны.
- `infra/` — локальная инфраструктура и настройки её запуска.
- `tests/integration/` — проверки связки компонентов, Docker и PostgreSQL.
- `apps/` — место будущего интерфейса.
- `old_monolit/` — исходник для сравнения функций. Новое приложение не должно импортировать его при запуске.
- `docs/` — короткие описания архитектуры, состояния и проверок.

## Кодогенератор

- Это отдельная утилита для любых проектов, а не часть бизнес-логики Lectify.
- Не зашивай в него имена сервисов, модели приложения, ACL и маршруты бизнес-вызовов.
- Зависимости и имена сервисов задаются манифестами проекта. Адаптеры Lectify находятся в сервисных `src/`.
- Сначала проверь, где проходит граница между универсальной инфраструктурой и приложением. Отделение ещё не завершено.
- Не редактируй `generated/` вручную: меняй шаблон или генератор и перегенерируй код.
- Генерация не должна уничтожать пользовательский `src/` и тесты.
- Не создавай отдельный `utils/test.py` или `utils/test_runner`: общий запуск тестов принадлежит codegen CLI.
- Тесты самой утилиты остаются в `utils/codegen/tests/`; проверки приложения — рядом с сервисом или в `tests/integration/`.

## Проверки

Из корня проекта:

```sh
export CODEGEN_ROOT="$PWD"
python3 utils/codegen/src/cli.py project
python3 utils/codegen/src/cli.py test
python3 -m pytest utils/codegen/tests -q
python3 -m pytest tests/integration/test_agent_backends.py tests/integration/test_controlled_image_cleanup.py -q
```

Генерация должна завершиться до запуска тестов. Пустые манифесты могут пропускаться с предупреждением — это незавершённые сервисы.
gRPC-тестам нужны локальные TCP-порты. Некоторым интеграционным скриптам нужны Docker или PostgreSQL.
Не называй проверку успешной, если запуск заблокирован окружением. Наличие protobuf или unit-теста не доказывает работу всего приложения.

## Что осталось

Автоматический запуск агентов и выдача сертификатов; завершение profile, personal и политики LLM;
media converter, prompt selector, LaTeX и PDF; восстановление после сбоев, pause/resume/retry;
полный запуск, миграции и проверки нескольких реплик. Клиентский HTTP API и UI — отдельный будущий этап.
Состояние уточняй по коду и тестам, а не по старым отчётам.

## Порядок работы

- Перед правками смотри `git status`; сохраняй чужие и незавершённые изменения.
- Удаляй подтверждённый мусор; не удаляй исходники, данные, секреты и пользовательские файлы по предположению.
- Не возвращай Telegram-мост и его автоматизацию. Связь с пользователем — в текущем чате.
- Секреты не выводить, не копировать в код, документацию и коммиты. `.secrets/` и `.env` должны оставаться исключёнными из Git.
- Платные внешние вызовы выполнять только с явным разрешением и ограниченным бюджетом.
- Документацию и ответы пиши простым русским языком. Указывай, что сделано, что проверено и что осталось.
